# Functional dependencies

A functional dependency (FD) says that a determinant value fixes a dependent value. The following dependencies are inferred from declared primary and unique constraints and the intended entity meaning. They are not claims about additional database uniqueness unless a constraint is named.

## Candidate keys and dependencies

| Table | Declared candidate key(s) | Main dependencies |
|---|---|---|
| User | `id`; nullable unique `email`, `phone`, `googleSubject` | `id →` all user attributes; each non-null unique identifier → `id` and its row |
| Department | `id`; unique `name`, `code`; nullable unique `headUserId` | `id →` all attrs; `name → id`; `code → id`; non-null `headUserId → id` |
| Category | `id`; unique `name` | `id →` all attrs; `name → id` |
| Ward | `id`; unique `name` | `id →` all attrs; `name → id` |
| Issue | `id`; unique `code` | `id →` all attrs; `code → id` |
| Complaint | `id`; unique `code` | `id →` all attrs; `code → id` |
| StatusHistory | `id` | `id →` all attrs |
| Transfer | `id` | `id →` all attrs |
| Message | `id` | `id →` all attrs |
| Feedback | `id`; unique `complaintId` | `id →` all attrs; `complaintId →` all attrs |
| Notification | `id` | `id →` all attrs |
| Setting | `key` | `key → value, updatedAt` |
| PasswordResetToken | `id`; unique `tokenHash` | `id →` all attrs; `tokenHash → id` |
| SensitivePlace | `id` | `id →` all attrs |
| GoogleLoginTicket | `tokenHash` | `tokenHash → userId, expiresAt` |

Nullable unique constraints in PostgreSQL normally permit multiple nulls, so the alternate key statements apply only when the column is non-null. Prisma IDs are generated by the client-side `cuid()` default in the model definition.

## Partial dependencies

The inspected models use single-column primary keys; no composite primary key is declared. Therefore there is no demonstrated partial dependency on only part of a declared composite key. Multi-column indexes such as `Complaint(citizenId, createdAt)` are access paths, not composite candidate keys.

## Transitive dependencies and boundaries

Within each row, descriptive attributes of related entities are generally stored in their own table and reached by foreign key. For example, `Complaint.departmentId` determines the referenced `Department` row's name only across the relation; the department name is not copied into the complaint table. Likewise, `Category.departmentId` points to a department rather than copying department details.

`Complaint.departmentId` and `Complaint.categoryId` can each refer to independently selected rows. Because Category itself points to a Department, a category and complaint department could disagree unless application logic checks this; no composite FK enforces the equality. Treat this as a domain integrity consideration, not proof of a normalization violation.

`Issue.reportCount`, `Issue.priority`, and `Issue.status` summarize or coordinate related complaint state. `Complaint.priorityReason`/priority and text variants are operational attributes. They can be redundant with derivable information or history, but their precise maintenance is workflow-specific. This documentation does not claim a proven FD from a non-key field; updates should be kept consistent by application logic.
