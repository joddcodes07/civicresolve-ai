# Constraints and validation

This inventory comes from Prisma schema and checked-in migrations, not a live catalog query.

## PostgreSQL-enforced rules

- **Primary keys / NOT NULL:** every model has a primary key; non-null Prisma fields map to non-null database columns. Examples include `Complaint.code`, `originalText`, coordinates, `slaHours`, `dueAt` and `Department.code`.
- **UNIQUE:** user email, phone and Google subject; department name/code/head user; category name; ward name; issue code; complaint code; feedback complaint ID; password reset token hash. Nullable unique fields permit multiple nulls in PostgreSQL.
- **Foreign keys:** relations in the schema prevent dangling references. Optional relation fields allow null. Complaint children (history, transfer, message, feedback, notification) use cascade delete in the declared Prisma relation; password reset and Google login rows cascade on user deletion. Some other FKs use PostgreSQL's default NO ACTION behavior.
- **Enums:** PostgreSQL enum types restrict User role, Complaint status, Issue status, Message sender role, and Notification channel to declared values.
- **CHECK:** no Prisma or migration CHECK constraints were found. In particular, rating/severity ranges and geographic bounds are not enforced by database CHECK constraints.
- **Defaults:** database migration defaults include status/role/channel and boolean/count/time defaults. `cuid()` IDs are generated by Prisma Client rather than a PostgreSQL default. `@updatedAt` is maintained by Prisma Client.

## Application validation

Zod schemas validate registration, login, message, feedback and other request fields before persistence. Complaint routes also check text length and location; `validatePuneLocation` checks a stored boundary or a development fallback. Such checks protect API paths but can be bypassed by direct SQL, so they are not substitutes for database constraints.

Examples: `server/src/routes/auth.routes.js`, `server/src/routes/complaints.routes.js`, `server/src/middleware/validate.js`, and `server/src/services/submissionService.js`.

## Validation demonstration

No intentionally invalid insert was executed. A future test should violate an actual FK (for example, a complaint referencing a nonexistent department) inside a transaction on a disposable migrated database, capture the PostgreSQL FK error, and roll back. Do not infer a successful rejection output without running it.
